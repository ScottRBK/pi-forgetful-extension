The seamless recall path

It is invisible, but not literally asynchronous: useful memory must arrive before Pi sends the main model request. A strict timeout keeps this preflight small.

sequenceDiagram participant U as User participant P as Pi extension participant M as Selected Pi model participant F as Forgetful service participant A as Main Pi agent U->>P: Normal prompt P->>P: Skip trivial or repeated prompts alt planning is needed P->>M: Small JSON search-planning request M-->>P: topic, intent, optional entities else fast path P->>P: prompt + cached session topic end P->>F: Project-scoped semantic search F-->>P: Bounded memory pack P->>A: Temporary context + deeper-search leads opt Agent needs more detail A->>P: forgetful_recall tool P->>F: Focused follow-up search F-->>A: Deeper bounded context end A-->>U: Normal answer
Pi explicitly supports this: before_agent_start can modify the system prompt for the current turn, while modelRegistry resolves existing models and credentials.

Leave the main agent useful “nuggets”

The preflight should inject only the strongest context plus short leads such as memory IDs, entity names, and related topics. The extension can also register a compact forgetful_recall tool so the main agent can decide to dig deeper during the same turn without asking the user to run anything.

What “background” means

Recall: invisible preflight

It briefly waits before the main agent starts, because late context cannot affect the first model request safely.

Capture: true background work

After agent_settled, a conservative model pass can extract and save durable decisions while the user reads the answer.

Timeout: continue without memory

If either the model or Forgetful is slow, Pi continues normally and a circuit breaker avoids repeated delays.

Pi extension

Owns timing, model selection, timeouts, caching, debug UI, and temporary injection. It contains no memory business rules beyond safety limits.

Direct model call

Use Pi's bundled complete() API and resolved auth. A separate subprocess agent is unnecessary and would add startup and tool overhead.

Warm Forgetful service

Use the REST search endpoint over localhost or a configured server. Do not rebuild the local Python runtime and embedding model for every prompt.

Agent recall tool

Register one bounded read-only tool for deeper exploration. Render it as a compact “memory lookup” line and cap calls/results to avoid tool-loop noise.

The adaptive planner is the Pi model

Application code should not guess whether “do it”, “what about Sarah?”, or an error string needs memory. Every normal user prompt goes to the configured Pi model, which returns a small validated search plan.

Do not call the planner in process-only cases

These checks know nothing about the meaning of the user's words. They only prevent recursion or duplicate work.

  • The user explicitly switched Forgetful off.
  • The message was generated by this extension, not typed by the user.
  • Pi retried the exact same input and its plan is already cached.

Model decides

  • Whether any search is useful.
  • One or two topic queries and the task intent.
  • Named entities and whether deeper graph lookup may help.

Code validates

  • Strict JSON shape and bounded field lengths.
  • Maximum query/entity counts and project scope.
  • Timeout, cancellation, caching, and failure-open behavior.
In other words: every new user prompt is judged by the selected Pi model. Code skips only messages that are not new user work, then validates the model's output and enforces safety limits.

Configurable prompt policy, protected contracts

The extension should let users and trusted projects shape memory judgment without allowing an override to break JSON parsing, scope limits, or safety rules.

Simple layering

Built-in core + optional global policy + optional trusted project policy. Policies append to the core rather than replacing it, so upgrades can preserve the extension's contract.

Small management surface

/forgetful prompts shows active sources and hashes; /forgetful prompt edit capture opens the selected policy file; /forgetful prompt test classification runs a debug-only dry run.

The recall prompt is an injection template, not another model call. Adding a second relevance model after search would improve filtering but work against the latency goal; the main agent can judge the bounded results and follow nuggets.

Automatic capture after the answer

Capture is feasible, but it is the riskier half. It should be conservative, create-only, governed by the active project/global scope, and unable to update or obsolete existing memory.

Store automatically

  • Confirmed decisions and user preferences.
  • Root cause plus validated solution.
  • Project conventions likely to matter again.
  • Useful constraints with evidence from the completed turn.

Never store automatically

  • Raw transcripts or routine tool output.
  • Unverified guesses and abandoned approaches.
  • Secrets, credentials, payroll data, or unnecessary PII.
  • Entities, updates, or obsolescence in the first version.
Capture lifecycle
  1. 1. Wait for success
    Run only after agent_settled; skip aborted or failed work.
  2. 2. Read the delta
    Review only messages since the last capture watermark.
  3. 3. Extract candidates
    Selected Pi model returns zero to three atomic, evidenced candidates.
  4. 4. Check overlap
    Query Forgetful for each candidate before any create operation.
  5. 5. Create or skip
    Create only novel high-confidence facts; never rewrite history silently.

Off

Recall still works; no capture model or writes run.

Observe

Generate and score candidates, show them only in debug, but write nothing. Use this while tuning the capture prompt and thresholds.

Auto

Seamless target mode after observe-mode acceptance. Save quietly and show only a small count in status/debug.

Project/global scope applies to both recall and capture. If overlap suggests an existing memory is incomplete or contradicted, auto mode skips it; updates and obsolescence remain explicit user-controlled actions.

Safety and failure boundaries

Risk Boundary
Memory prompt injection Label retrieval as untrusted historical context, never instructions.
Cross-project leakage Default to strict repository scope, but expose a session/global toggle: /forgetful scope project or /forgetful scope global. Debug mode always shows the scope.
Slow or unavailable service Hard timeout, fail open, and circuit-break repeated failures.
Conversation clutter Modify only the per-turn system prompt; render deeper agent lookups as one collapsed line rather than exposing raw retrieval output.
Runaway memory exploration Read-only tool, strict project scope, bounded depth, and per-turn call cap.
Duplicate or noisy capture Query-before-create, high confidence, create-only, bounded candidates.
Unexpected model cost User-selected model, adaptive invocation, visible usage in debug mode.

Slice 1 acceptance checks

  • Normal prompt requires no memory command.
  • Relevant memory reaches the same main-agent turn.
  • The agent can follow a lead with the bounded recall tool.
  • No custom memory message is written to session history.
  • Timeout or service failure never blocks the task.
  • Measured first-token overhead meets the agreed p50/p95 SLO.
  • Off, on, debug, project, and global modes work without restarting Pi.
